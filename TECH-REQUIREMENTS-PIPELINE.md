# Технические требования к пайплайну генерации техпаков

**Проект: [рабочее имя — придумать, «Seamster» занято конкурентом]** · v1.0 · 2026-07-16
Основание: база знаний `knowledge-base/00–07` + конкурентная разведка (21 ответ AI-консультанта конкурента) + карта сегментов (С1 основатели брендов, С2 селлеры).

---

## 0. Продуктовый принцип

**Конкурент генерирует картинки с полями и говорит «доработайте сами». Мы генерируем СТРУКТУРИРОВАННЫЕ ДАННЫЕ изделия, из которых рендерится документ, который примет фабрика.**

Три следствия, определяющие всю архитектуру:

1. **Single source of truth — StyleSpec (JSON)**, а не набор изображений. Флэты, таблицы, PDF — проекции этих данных. Поправил замер → флэт перерисовался (дифференциатор №7, у конкурента признанно отсутствует).
2. **Каждое значение несёт confidence-флаг**: `user_input | estimated_from_photo | default_from_base | assumption`. Невидимое с фото никогда не подставляется молча (у конкурента — «считайте всё черновиком»).
3. **Метрика качества продукта = чек-лист технолога** (knowledge-base 07, §6): комплектность, однозначность, POM с допусками, узлы под парк машин, расчётопригодность. Не «красивый PDF», а «фабрика приняла без вопросов».

## 2. Архитектура (модули)

```
[A. Intake]──►[B. Vision Analysis]──►[C. Spec Assembly Engine]──►[D. Renderers]──►[E. Editor/Export]
                                          ▲
                     [KB: справочники ← knowledge-base 01–07 как data-файлы]
```

### A. Intake (входные данные)

- Загрузка 1–6 фото (референс: фото изделия / скрин карточки / эскиз).
- **Обязательные вопросы пользователю** (якоря, которые нельзя извлечь из фото — 03, §5):
  1. Базовый размер + рост («RU 46 / M, рост 170»)
  2. Fit-intent (прилегающий / полуприлегающий / свободный / oversize)
  3. Трикотаж или ткань (если не очевидно с фото)
  4. Размерный ряд (например 42–52)
  5. Тираж и колорвеи (для SKU-матрицы и labels)
- Опциональные усилители точности: предмет-референс в кадре (А4/карта), один ручной замер (линейно калибрует всё), данные бренда (юрлицо для ярлыков).

### B. Vision Analysis (мультимодальная LLM, Claude API)

Вход: фото. Выход: **строго типизированный JSON** (не свободный текст):

- `category` + уверенность; silhouette/fit-класс;
- `visible_elements[]`: тип горловины, карманы (тип+положение), манжеты/пояс (риб vs подгибка), застёжка, кулиски/люверсы, видимые отстрочки (число параллельных строчек!), швы с видимой структурой (флэтлок/запошивочный);
- `proportions{}`: безразмерные отношения по keypoints (длина/ширина груди, рукав/длина, позиция кармана в % и т.д.);
- `colorways[]`, фактура материала (класс: кулирка/футер/рибана — по 05, §1 «определимо с фото»);
- `not_visible[]`: явный список того, чего модель НЕ видит (изнанка, прокладки) — уходит в assumptions.
  Промпт опирается на карту «видно/не видно» (04, §7). Несколько фото → merge с приоритетом более детального вида.

### C. Spec Assembly Engine (детерминированный код + справочники)

Ядро продукта. Собирает `StyleSpec`:

1. **POM Engine** (03): шаблон точек категории → якорь chest из (размер тела по ГОСТ-сетке + ease по fit-intent) → остальные значения = якорь × пропорции с фото → клэмп в диапазоны категории → **допуски автоматом** по классам точек → **автоградация** по типовым приращениям RU (редактируемая) → флаги на каждое значение.
2. **Construction Engine** (04): дефолтный набор узлов категории → корректировка по visible_elements (увидели 2 параллельные строчки низа → 406; двойную отстрочку — 401) → каждому узлу: код шва/стежка ГОСТ=ISO, SPI, тип машины, припуск → **machine-park check**: узел вне тройки «универсалка+оверлок+распошив» получает флаг `special_equipment` + автоматически предлагается альтернативный узел (07, §5) → невидимые узлы = `assumption: true`.
3. **BOM Engine** (05): материалы по категории+фактуре с фото (класс полотна, GSM-дефолт с флагом), фурнитура из visible_elements (молния № по типу изделия, люверсы и т.п.), нитки, прокладки-assumption, Pantone с фото («сверить по выкрасу»), **предварительный расход** по формулам 05 §3.2 с пометкой «уточняется фабрикой по раскладке» (конкурент отказался это делать — а фабрике нужно для калькуляции).
4. **Labels/RF Module** (06): слой изделия по ТР ТС → форма подтверждения; макеты ярлыков (care label с 5 символами ухода по дефолту материала, брендовый, размерник, hangtag); **SKU-матрица** (артикул × цвет × размер) с GTIN-плейсхолдерами.
5. **Tech Sequence Generator** (04, §5): технологическая последовательность (№, операция, специальность М/С/А/Р/У/П, оборудование) из набора узлов.

### D. Renderers (проекции StyleSpec)

1. **SVG Flat Renderer**: параметрический шаблон категории (front/back), геометрия управляется пропорциями из StyleSpec; конвенции линий из 02 §3 (outline 2pt / швы 1pt / отстрочки dash 0.5pt / скрытое dot); символьная библиотека 02 §4; нумерованные callouts, синхронные с конструкцией/BOM. Слои: `outline / seams / stitches / hardware / callouts` (послойный SVG — у конкурента нет).
2. **POM Diagram Renderer**: тот же флэт + стрелки замеров с кодами.
3. **Document Renderer**: HTML → PDF (A4 landscape, секция = страница, по 01 §1): cover → flats → BOM → табель мер с допусками и градацией → конструкция+техпоследовательность → labels/SKU → страница-заглушка «лекала/раскладка — предоставляется конструктором». Двуязычные термины (RU лид + EN в скобках).
4. **Экспорт по ролям** (07, §6.6): один клик → отдельные PDF: «для ОТК» (табель мер), «для закройщика» (спецификация), «для снабжения» (BOM+расход), «полный».

### E. Editor / Versioning

- Все поля StyleSpec редактируемы; правка данных → live-перерисовка флэта и таблиц.
- Ревизии: снапшот StyleSpec на каждое сохранение; `SampleRound` + `FitComment` (спека vs факт замера, в допуске?, действие) — по 01 §4.
- Экспортные форматы: PDF, послойный SVG; DXF — в roadmap (passthrough файлов конструктора — сразу).

## 3. Схема данных

Реляционная модель — knowledge-base 01 §3 (Style / Colorway / Material / BOMLine / POMDef / POMValue / GradeRule / ConstructionOp / Label / SKU / SampleRound / FitComment + `confidence_flag` везде). Для MVP: Postgres (или SQLite на старте) + JSON-снапшоты StyleSpec.

**Дополнения из разведки схемы конкурента (их схема получена полностью — наша является надмножеством):**

- Заимствуем: (1) допуск по умолчанию на таблицу мер + `tolerance_override` на конкретную точку; (2) `diagram_url` (мини-диаграмма «как мерить») у каждой POM-точки — критично для С1, не знающего терминов; (3) референсные изображения хранятся в паке для сравнения и fit comments.
- Их структурные дыры (не воспроизводить): colorway как строка (нет BOM-на-колорвей и SKU-матрицы); визуалы как файлы-URL без связи с данными; материалы без библиотеки (нет переиспользования между моделями); нет GradeRule; нет Revision/SampleRound/FitComment; stitch_type свободным текстом (нет кодов/SPI/машин). Вывод: их ядро — «документ с картинками», наше — «цифровая модель изделия»; догнать добавлением колонок нельзя.

## 4. Справочники (KB-файлы = код)

Из базы знаний выделяются машиночитаемые справочники (JSON/YAML), версионируемые в репо:
`size_charts_ru.json` (ГОСТ-сетки) · `ease_defaults.json` · `pom_templates/{category}.json` · `grading_increments.json` · `tolerance_classes.json` · `construction_nodes.json` (узлы: коды, припуски, машины, видимость) · `category_defaults/{category}.json` · `materials.json` · `hardware.json` · `care_symbols.json` · `consumption_formulas.json` · `machine_park_profiles.json` (базовый цех / расширенный).
⚠️ Помеченные ★/⚠️ значения из KB переносятся с полем `verified: false` — обновляются по результатам отшивов и интервью технологов.

## 5. Требования-дифференциаторы (трассировка к провалам конкурента)

| #   | Требование                                                                                           | Провал конкурента                     |
| --- | ---------------------------------------------------------------------------------------------------- | ------------------------------------- |
| R1  | Якорь масштаба от пользователя (размер+рост+fit), не «дефолтный M системы»                           | отв. 1                                |
| R2  | Допуски автоматом по классам точек, редактируемые                                                    | отв. 2 («не устанавливаем»)           |
| R3  | Автоградация RU-приращениями + ростовки, редактируемая                                               | отв. 3 («только базовый»)             |
| R4  | Confidence-флаги на каждом значении + блок «TO CONFIRM AT PROTO»                                     | отв. 4 («не помечаем»)                |
| R5  | Коды швов/стежков ГОСТ=ISO + SPI + машина на операцию                                                | отв. 9 («вносите вручную»)            |
| R6  | Machine-park check + альтернативный узел                                                             | отв. 10 («не знаем про оборудование») |
| R7  | Единая модель данных: правка замера → обновление флэта                                               | отв. 12 («не обновятся»)              |
| R8  | Ревизии + fit comments (sample rounds)                                                               | отв. 13 («дублируйте проект»)         |
| R9  | РФ-слой: ярлыки ТР ТС + символы ухода + SKU/Честный знак + предварительный расход + экспорт по ролям | отв. 14–17 (пусто)                    |
| R10 | Параметрический вектор: флэт редактируется данными, не перегенерацией                                | отв. 11 («SVG в Illustrator»)         |

Перенимаем у конкурента: кредиты только за успешные генерации; бесплатный повтор запуска; тип/ткань/цвет спрашиваются на входе; честность про лекала и слабые категории.

**Разведданные об их image-пайплайне (важно):** конкурент генерирует ВСЕ изображения через gpt-image-2 (растровая genAI-модель) → трассировка в SVG (их UI «line pickup / noise cleanup / curve smoothness» = крутилки векторизации растра). Следствия:

- их флэты принципиально нередактируемы данными и невоспроизводимы (генеративная вариативность) — R7/R10 для них недостижимы без смены архитектуры → **параметрический SVG = защитимый ров, приоритет R10 повышен**;
- их себестоимость генерации = токены image-модели на каждую итерацию; наш SVG-рендер из данных ≈ бесплатен → преимущество в юнит-экономике и в цене повторных правок;
- genAI-изображения в нашем продукте допустимы ТОЛЬКО для фотореалистичных превью/маркетинговых рендеров (отдельный опциональный модуль, вне технической геометрии). Техническая геометрия — всегда детерминированный вектор из StyleSpec.

## 6. Нефункциональные требования

- **Воспроизводимость:** одинаковый вход → одинаковый StyleSpec (температура LLM ↓, детерминированный assembly). Урок The New Black.
- **Язык:** RU-первый, термины дублируются EN.
- **Время генерации:** ≤ 5 мин полный пакет (v0.1 допускает асинхронность).
- **Себестоимость на техпак:** считать с первого дня (LLM-токены + human-QA) — вход в A5 (маржа ≥50% при чеке 3–5 тыс. ₽).
- **Human-QA слой (v0.1):** каждый concierge-выпуск проверяет человек с чек-листом технолога; расхождения → правки справочников (петля обучения без ML-трейнинга).

## 8. Приёмочные критерии MVP

1. По 10 тестовым фото (по категориям) генерируется полный пакет без падений; повторный прогон → идентичный StyleSpec.
2. Технолог по чек-листу 07 §6 оценивает пакет ≥ 7/9 пунктов (лекала/образец — заглушки по дизайну).
3. **≥ 60% фабрик артефакт-теста берут документ в работу для отшива пробника** (kill-критерий RAT-1: ≤ 2 из 7 — пивот архитектуры ценности).
4. Пробник по нашему техпаку: ≤ 2 итерации до утверждения (паритет с конструктором, RAT-3).
5. Ни одного «молчаливого» значения: каждое поле имеет источник (user/photo/default/assumption).

## 9. Открытые решения (не блокируют старт)

- Имя продукта (Seamster занят).
- SVG-параметрика: своя геометрия vs заготовки художника с контрольными точками (решить на этапе 3 прототипом).
- 3D-рендеры: только как маркетинговая фича позже.
- DXF-экспорт лекал: после партнёрства с конструкторами/САПР.
