## 1. Главный конфликт, который надо разрешить до первой строки кода

`CTO-SPEC.md` §3 ставит жёсткий стоп-кран: **веб-приложение не строится, пока RAT-1 не сказал «фабрики берут документ в работу»**. Разрешённая работа в окне теста: голден-тесты, справочники, concierge-исполнение через CLI, лендинг с waitlist.

При этом готовы дизайн-макеты всего приложения — соблазн начать с фронтенда высокий.

**Моя рекомендация: движок первым, и вот почему это не догматизм.**

1. Фронтенд без StyleSpec — это верстка по выдуманным данным. Таблица замеров с градацией, статусы уверенности, live-связь чертёж↔данные, machine-park check — всё это UI **над структурой, которой пока нет**. Сделаем UI раньше — перепишем его, когда схема устаканится. Это не «дисциплина ради дисциплины», это порядок зависимостей.
2. RAT-1 требует **три PDF-техпака**, а не приложение. Фабрике всё равно, есть ли у нас дашборд.
3. Если RAT-1 провалится, весь фронтенд — списанные недели. Если пройдёт — движок уже есть, и фронт кладётся на готовые данные втрое быстрее.
4. Дизайн не протухнет: макеты зафиксированы в хендоффе с точностью до токена.

**Что при этом фронтенд НЕ простаивает:** в окне RAT-1 (3–4 недели ожидания ответов фабрик) строим лендинг с waitlist — он прямо разрешён стоп-краном и нужен для RAT-4 (автономный канал). Лендинг делается на тех же дизайн-токенах и компонентной базе, что и приложение → к моменту гейта у нас уже есть половина дизайн-системы приложения. Это честный способ двигать фронт, не нарушая стоп-кран.

> ✅ **Решение CEO от 2026-08-25: движок первым.** Порядок принят как описано выше.

## 3. Технические поправки к спекам (спека расходится с реальностью API)

Это не придирки — это места, где текущая спека физически неисполнима.

### П1. «Temperature минимальная» больше не существует

`TECH-REQUIREMENTS-PIPELINE.md` §6 и `CTO-SPEC.md` §1.2 закладывают детерминизм через низкую температуру. **На актуальных моделях Claude (Opus 5, Sonnet 5) параметры сэмплирования `temperature`/`top_p`/`top_k` удалены — запрос с ними возвращает 400.** Детерминизм этим способом недостижим в принципе.

**Как получаем 100% воспроизводимости на самом деле:**

```
VisionReport = cache[ sha256(фото ⊕ prompt_version ⊕ model_id ⊕ schema_version) ]
```

- Vision-этап вызывается один раз на уникальный вход, результат кладётся в контент-адресуемый кэш (БД + объектное хранилище). Повторный прогон того же входа → тот же `VisionReport` → тот же StyleSpec. Байт в байт.
- Assembly, рендеры, документ — **чистые детерминированные функции** без обращения к LLM. Здесь воспроизводимость гарантируется кодом, а не моделью.
- Смена промпта или модели = смена ключа кэша = явная миграция с прогоном голден-сета. Дрейф точности становится видимым событием, а не тихой деградацией.

Это ещё и экономит деньги: бесплатный повтор генерации после ошибки рендера не тратит vision-токены.

### П2. Structured output — актуальный синтаксис

Схема задаётся через `output_config: { format: {...} }` (параметр `output_format` устарел), для инструментов — `strict: true` в определении инструмента. Валидация ответа против JSON Schema — на стороне API, ретрай при несовпадении — тоже. Это ровно то, что нужно для `VisionReport`: типизированный выход без парсинга свободного текста.

### П3. Себестоимость: узкое место — не токены, а человек

Прикидка на генерацию (6 фото + справочный контекст ≈ 14k входных токенов, структурированный JSON ≈ 4k выходных) на Opus 5 ($5 / $25 за 1M) — **порядка $0.15–0.25 за техпак**. При чеке 3–5 тыс. ₽ это доли процента.

Вывод, который меняет приоритеты: **цель «COGS ≤ 20%» упирается не в inference, а в ручной QA технолога.** Оптимизировать надо не модель, а долю паков, проходящих без ручной правки. Поэтому таксономия ошибок QA и автовалидаторы StyleSpec — это работа по юнит-экономике, а не «качество на потом». Дешёвые модели на простых этапах и Batch API (−50%) держим в резерве, но это не рычаг.

Токены/стоимость логируем на каждой стадии с первого дня — как требует `CTO-SPEC.md` §1.6.

### П4. Модели

Фаза 0 — **`claude-opus-5`** на vision. RAT-1 — про точность; экономить на ней сейчас нельзя. После набора статистики на голден-сете пробуем `claude-sonnet-5` и меряем деградацию; переключение — за флагом конфига, решение по данным.

### П5. Claude API и 152-ФЗ

Два независимых вопроса:

- **Технический:** доступ к API из РФ-контура. Нужен исходящий прокси или зарубежное юрлицо/платёжка. Решается инфраструктурно, но требует решения до продакшна.
- **Юридический:** персональные данные (email, реквизиты бренда) остаются в РФ-контуре — БД и хранилище на РФ-хостинге. Наружу уходят **только фото изделий**, которые персональными данными не являются. Архитектурно разделяем эти два потока с первого дня, чтобы потом не переезжать. Формулировку в оферту/политику — с юристом.

### П6. Параметрический SVG — снимаю с этого риск-статус

`CTO-SPEC.md` §5 держит параметрику как риск №1 с чекпоинтом на неделе 2 и фолбэком «заготовки художника с контрольными точками».

**Считаю, что фолбэк должен быть основным подходом с самого начала.** Требование рва (R7/R10) звучит как «правка замера обновляет чертёж» — оно **не** требует синтеза геометрии с нуля. Мастер-шаблон категории с именованными контрольными точками, деформируемый пропорциями из StyleSpec, удовлетворяет R7/R10 полностью, и при этом:

- даёт профессиональное качество линий сразу, а не после недель возни с безье;
- новая категория = нарисовать мастер + разметить якоря (дни, не недели);
- элементы (карманы, манжеты, капюшон, планка) — библиотека символов, композитятся поверх.

Процедурная генерация с нуля даёт «чертёж, нарисованный программистом» — на приёмке у технолога это минус. Чекпоинт недели 2 оставляю, но показываю тебе оба варианта рядом и жду решения по картинке, а не по описанию.

## 5. Дорожная карта

### ФАЗА 0 — «Станок». Недели 1–3. Выход: 3 PDF для RAT-1

**Неделя 1 — фундамент и данные**

- Репозиторий, CI (прогон голден-сета на каждый PR), Docker Compose, CHANGELOG, ADR-0…4.
- KB → JSON с zod-схемами и тестами: `size_charts_ru`, `ease_defaults`, `tolerance_classes`, `grading_increments`, `pom_templates/tshirt` (T01–T18 с how-to-measure и классом точки), `construction_nodes`, `stitch_codes`, `seam_codes`, `machine_park_profiles`, `materials`, `hardware`, `care_symbols`, `consumption_formulas`, `category_defaults/tshirt`, `visibility_map`. Все значения с пометкой ★/⚠️ из KB переносятся с `verified: false` и ссылкой на источник.
- JSON Schema `StyleSpec` v0.1 + 3 рукописных эталона.
- Vision-промпт v1 со structured output → прогон на 5 фото → **отчёт CEO: что распознаётся уверенно, что нет.**

**Неделя 2 — движки + чекпоинт рва**

- POM Engine: якорь (размер+рост+посадка) → сетка ГОСТ + ease → пропорции с фото → клэмп в диапазоны → допуски по классам точек → автоградация. Каждое значение с `confidence` и происхождением.
- Construction Engine: дефолты категории → корректировка по `visible_elements` → коды ГОСТ=ISO + SPI + машина + припуск → machine-park check → альтернативный узел → невидимое помечается `assumption`.
- BOM Engine (+ предварительный расход), Labels Engine (символы ухода, ТР ТС, SKU-матрица), TechSequence Generator.
- Валидаторы StyleSpec: диапазоны, кросс-проверки POM↔категория, «ни одного значения без источника».
- **Чекпоинт: SVG-флэт «футболка» перед/спинка — два подхода рядом, решение CEO по картинке.**

**Неделя 3 — документ и артефакты**

- Document Renderer: HTML→PDF, A4 landscape, все страницы, легенда статусов на стр. 1, термины RU + EN. Экспорт по ролям (технолог / закройщик / ОТК / снабжение).
- CLI: `specform generate --photos ... --answers ... --out pack.pdf`.
- Учёт стоимости по стадиям.
- Прогон 3 реальных референсов (худи, футболка, лонгслив) → ручная доводка → **3 артефакта для похода по фабрикам**.
- Голден-харнесс: 10 фото, снапшот-тесты, гейт в CI.

**DoD:** 10 эталонных фото проходят пайплайн без падений · повторный прогон даёт идентичный StyleSpec · себестоимость посчитана · 3 PDF у CEO.
